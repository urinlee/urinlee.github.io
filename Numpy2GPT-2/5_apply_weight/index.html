NumPy로 GPT-2 구현 | 5. 사전 학습 가중치 적용과 Hugging Face 출력 비교

posted by 지티오,
November 11, 2026

앞 글에서 GPT-2의 계산 과정을 연결했다. 이번에는 공개 GPT-2 가중치를 적용하고, Hugging Face(HF) 모델과 출력이 얼마나 같은지 비교했다.

먼저 어느 함수에 어떤 가중치를 넣는지, 그 가중치를 원본 파일 어디에서 가져오는지 정리한다. 이어서 실제 logits와 오차를 확인하고, 같은 가중치인데도 차이가 생긴 이유를 살펴본다.

1. 가중치가 필요한 곳

@는 행렬 곱셈, W는 입력에 곱하는 행렬, b는 결과에 더하는 편향(bias) 벡터다. W와 b 모두 학습된 값을 파일에서 가져온다.

임베딩 — forward()

토큰 ID와 위치를 벡터로 바꾸는 표가 필요하다. wte는 토큰 임베딩 표, wpe는 위치 임베딩 표다.

입력 벡터 = wte[토큰 ID] + wpe[위치]

LayerNorm — layer_norm()

정규화한 벡터에 곱할 gamma와 더할 beta가 필요하다.

정규화된 x = (x - 평균) / √(분산 + ε)
출력 = gamma × 정규화된 x + beta

평균·분산은 입력에서 계산하고, ε는 나눗셈을 안정화하는 작은 상수다. 파일에서는 gamma, beta를 가져와 성분별로 적용한다.

Attention — multi_head_self_attention()

Q·K·V를 만들 때와 헤드를 합친 결과를 변환할 때 각각 W, b가 필요하다. x는 첫 LayerNorm을 통과한 입력이다.

Q = x @ W_Q + b_Q
K = x @ W_K + b_K
V = x @ W_V + b_V

출력 = 헤드를 합친 결과 @ W_O + b_O

어텐션 확률은 입력마다 계산하고, W, b는 파일에서 가져온다. Q·K·V로 확률을 구하는 과정은 Attention 글에서 다뤘다.

FFN — feed_forward()

벡터를 넓히는 W_1, b_1과 줄이는 W_2, b_2가 필요하다. x는 두 번째 LayerNorm을 통과한 입력이다.

중간값 = GELU(x @ W_1 + b_1)
출력 = 중간값 @ W_2 + b_2

GPT-2에서는 768 → 3072 → 768차원으로 계산한다. GELU 자체에는 가져올 가중치가 없다.

블록 연결 — forward()의 블록 반복

위의 LayerNorm·Attention·FFN을 순서대로 실행하고 잔차를 더한다.

h = x + Attention(LayerNorm_1(x))
출력 = h + FFN(LayerNorm_2(h))

각 함수의 가중치를 그대로 사용하며, 잔차를 더하는 데는 별도 가중치가 없다.

최종 출력 — forward()

마지막 LayerNorm의 gamma, beta를 적용한 뒤, 입력에서 썼던 wte를 다시 사용한다.

마지막 벡터 = LayerNorm_f(마지막 블록의 출력)
logits = 마지막 벡터 @ wte.T
확률 = softmax(logits)

wte.T는 wte의 행과 열을 바꾼 것이다. 출력층은 입력 임베딩을 공유하며, softmax에는 별도 가중치가 없다.

logits는 다음에 올 토큰 후보마다 매긴 점수다. 점수가 높을수록 모델이 더 유력하게 보는 후보이며, softmax를 적용하면 후보별 확률이 된다.

Q·K·V는 원본에서 하나로 붙어 있다. 그래서 c_attn.weight의 열을 앞 768개는 Q, 다음 768개는 K, 마지막 768개는 V로 나눈다. 편향도 같은 순서로 나눈다. 0:768은 인덱스 0~767을 뜻한다.

예를 들어 첫 블록의 W_Q는 h.0.attn.c_attn.weight의 앞 768개 열을 꺼내 weights["blocks.0.attn.W_Q"]에 넣으면 된다.

3. 기존 구현에 가중치를 넣고 비교하기

기존 NumPy 구현에 위 가중치를 넣고 HF의 GPT2LMHeadModel과 비교했다.

원래 Attention에 빠져 있던 b_Q, b_K, b_V, b_O를 반영했다. 예를 들어 Q는 Q = x @ W_Q + b_Q로 계산한다.

두 모델에 같은 가중치와 토큰 ID를 넣고 logits의 절대오차를 구했다. hf_model은 HF 모델이다.

from notebook_model import forward

numpy_logits = forward(token_ids, weights, config)["logits"]
with torch.inference_mode():
    hf_logits = hf_model(
        torch.tensor(token_ids[None, :]), use_cache=False,
    ).logits[0].numpy()

error = np.abs(numpy_logits - hf_logits)
print(error.max(), error.mean())  # 최대·평균 절대오차

모든 입력 위치에서 다음 토큰 후보 50,257개의 점수를 각각 대조했다. 최대 절대오차는 그중 가장 큰 차이이고, 평균 절대오차는 전체 차이의 평균이다.

가장 큰 차이가 난 위치

가장 큰 차이는 자연문 256토큰 입력의 228번째 위치에서 발생했다. 그 위치까지 읽은 뒤, 다음 토큰 후보 challeng(ID 4010)에 매긴 점수를 비교한 값이다.

내 구현: -68.972496151672
HF:      -68.980422973633

256·512·1,024토큰 자연문 입력에서 같은 위치의 차이가 유지됐고, 이 세 입력이 허용오차 검사를 통과하지 못했다. 기준은 각 값에 대해 오차 ≤ 0.0005 + 0.0001 × |HF logit|이었다.

즉, 가장 높은 점수를 받은 토큰은 모두 같았지만, logits의 숫자까지 같지는 않았다.

6. 같은 가중치인데 왜 차이가 났을까?

내 코드에서는 Attention 점수를 나누는 부분을 원래대로 유지했다.

head_scores = head_scores / np.sqrt(d_head)

현재 사용한 NumPy 2.5.4에서는 np.sqrt(d_head)가 float64 값을 만들고, 이 나눗셈부터 중간값도 float64가 된다. HF 모델은 float32로 계산했으므로, 기본 비교에서는 두 모델의 계산 정밀도가 달랐다.

float32와 float64는 중간값을 저장할 수 있는 정밀도가 달라, 계산 중 반올림 결과도 달라질 수 있다.

설명용 예시: 정밀도에 따른 반올림

계산: (100,000,000 + 1) - 100,000,000

float32 결과: 0
float64 결과: 1

float32는 이 크기에서 +1의 차이를 저장하지 못해 중간값이 반올림된다.

모델에서도 작은 차이가 이후 층의 계산에 영향을 줄 수 있다. float32 가중치를 float64로 바꿔도 가중치 값 자체는 유지되고, 이후 계산을 수행하는 정밀도가 달라진다.

중간 출력을 보니 임베딩은 정확히 같았고, 첫 블록부터 차이가 생겼다. 차이가 컸던 두 입력을 양쪽 모두 float64로 다시 계산했다.

다시 비교한 입력 기존 계산의 최대오차 양쪽 모두 float64일 때
자연문 256토큰 0.00792682 약 1.17 × 10⁻¹¹
0 128회 반복 0.00264310 약 2.59 × 10⁻¹²

두 입력 모두 차이가 크게 줄었다. HF 모델 자체도 같은 자연문 입력에서 float32와 float64 결과 사이에 최대 약 0.00749의 차이가 있었다.

이 재실험은 계산 정밀도가 오차의 주요 요인임을 뒷받침한다. 다만 float64 재실험은 두 입력만 확인한 결과다.

7. 샘플링 방식에 따른 출력 비교

앞에서는 두 구현의 logits를 비교했다. 이번에는 같은 NumPy 모델에서 다음 토큰을 고르는 방법만 바꿔 문장을 생성했다.

공통 입력은 앞에서 사용한 문장이다.

Hello, my name is

생성한 토큰을 입력 뒤에 하나씩 붙여 다시 순전파했다. 각 방식은 최대 40토큰을 생성하고, 무작위 선택을 하는 아홉 조건은 각각 시드 42로 시작했다. Greedy는 무작위 선택을 하지 않는다.

방식 비교한 설정
Greedy 점수가 가장 높은 토큰 선택
온도만 조절 T=0.1·1.0·2.0, 후보 제한 없음
Top-k k=50 고정, T=0.1·1.0·2.0 각각 적용
Top-p p=0.9 고정, T=0.1·1.0·2.0 각각 적용

Temperature는 softmax(logits / T)로 적용했다. top-k와 top-p에서도 먼저 온도를 적용한 뒤 후보를 제한했다. top-k는 상위 50개, top-p는 확률이 높은 순서로 누적합이 0.9 이상이 되는 최소 후보 집합에서 선택한다. 두 제한은 각각 따로 적용했다.

아래는 입력 문장까지 포함한 실제 출력이다. 열 결과 모두 종료 토큰이 나오기 전에 40토큰 한도에 도달했으므로, 문장 중간에서 끊긴 부분도 그대로 남겼다.
